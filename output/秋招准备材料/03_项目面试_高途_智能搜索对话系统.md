# 智能搜索对话系统

> PROJECT INTERVIEW BRIEF 03｜Query 标准化、实体证据、分层意图识别、动态检索路由与多层上下文

公司：高途教育集团 \| 部门：用户研发部算法研发组 \| 角色：核心成员 \| 时间：2026.02 - 2026.04

## 项目介绍口播

### 30 秒版本

我深度参与了高途 C 端主 App 搜索算法链路重构，负责 BERT 意图识别、检索/生成路由与会话上下文管理。意图侧以高置信 BERT 为主、低置信轻量 LLM 补判，再按最终意图分流至检索结果直返或大模型生成；上下文侧基于 Token 预算设计高低水位压缩，动态压缩陈旧轮次并保留近期原文，同时注入离线 FactMemory 补充长期事实。

### 2 分钟版本

高途 C 端搜索需要同时处理多类查询意图与跨轮承接。我负责 BERT 意图识别训练、检索/生成路由和会话上下文管理。训练侧基于真实用户问句构建实体增强样本，让模型学习实体类型与句式，并用类别权重、Focal Loss 和 Label Smoothing 处理长尾与 hard case；推理时高置信采用 BERT 结果，低置信由轻量 LLM 补判。最终意图确定后，检索类直接返回召回结果，知识问答与对话类进入回答 Prompt 和生成模型。上下文侧按 Token 精确计数维护高低水位，超过高水位后根据水位差动态压缩陈旧轮次，直至回落到低水位，并始终保留近期原文；同时读取离线 FactMemory 补充长期事实。历史 EventSummary 在线召回仍是后续规划，不作为已实现能力表述。

## 三、整体链路

Raw Query  
→ 全角转半角 → 繁简转换 → 实体词典驱动的拼音转汉字 → 空白清理 → 分词  
→ Evidence：精确匹配 → token 匹配 → 模糊/向量回退 → 去重融合  
→ Intent：BERT(高置信) → 轻量 LLM(低置信) → 演示规则兜底  
→ ResponseBuilder：实体 target/filter 萃取 + 只基于当前 Query 的意图覆盖  
→ 检索类：动态 Filter + 混合召回 + 乘法重排；生成类：LLM 回答  
→ SessionManager：保存本轮并更新 context entity / 多层上下文

## 四、算法设计

### 4.1 证据收集

- 精确匹配使用多模式词典；文档采用 FlashText/Trie 思路，适合大量实体别名一次扫描。

- token 匹配降低置信度，模糊匹配只作回退；证据按 (type,value) 去重保留最高分。

- 实体证据在意图识别前产生，因为 BERT 本身不知道‘白马老师=褚佳麟’，外置知识能帮助分类。

- 推理时用与训练端一致的实体类型标记，最长匹配避免长短别名相互覆盖。

### 4.2 BERT 分层意图识别

| **层**    | **条件**                                    | **作用**                          |
|-----------|---------------------------------------------|-----------------------------------|
| 本地 BERT | 纯文本 confidence ≥0.85；带图 ≥0.90 | 10-50ms 量级，先处理确定样本      |
| 轻量 LLM  | BERT 低置信或不可用                         | 64-token JSON 意图；处理长尾/歧义 |
| 规则兜底  | Demo 无 BERT/LLM                            | 保持主链可运行；生产不依赖这一层  |

训练数据约包括 1.4 万真实用户标注、1.4 万实体打标版、5.4 万模板×实体合成和约 1.9 万均衡合并版。核心不是死记实体名，而是学习“实体类型 + 句式 → 意图”，新增实体只需更新词典即可泛化。

### 4.3 类别不均衡与 hard case

- 类别权重解决频率不均衡，让长尾类在梯度中不被多数类淹没。

- Focal Loss 解决难度不均衡，降低 easy sample 权重，强调边界样本；gamma=2 是默认配置。

- Label Smoothing=0.1 缓解歧义样本过拟合并改善置信度校准，使阈值回退更可信。

- 以 weighted F1 选 checkpoint，连续 3 个 epoch 不提升 early stop；同时应关注各类 recall/F1，而不只看 accuracy。

### 4.4 动态检索与重排

只对课程、老师、产品功能等检索类意图访问向量库。Filter 先加 intent\_word 和 status=1，再把当前实体、上下文实体和画像作为可选召回约束。多个实体用 OR 保召回，再在排序阶段按当前实体×3、上下文×1.5、画像×1.2 做乘法增益；乘法能避免低基础相关性的垃圾结果被固定加分抬高。

## 五、上下文工程

| **层**                | **内容**                 | **注入方式**         | **原因**                      |
|-----------------------|--------------------------|----------------------|-------------------------------|
| FactMemory            | 稳定、浓缩的长期事实     | system context 全量  | 量少、信息密                  |
| EventSummary          | 历史 Session 摘要        | 规划按当前 Query RAG | V1 未实现在线召回             |
| 当前 Session 近期轮次 | 原始 user/assistant 消息 | messages 保真        | 支撑指代与连续对话            |
| 当前 Session 陈旧轮次 | 超过高水位后动态选择     | 摘要至低水位         | 保留近期原文并预留 Token 空间 |

- 原实现把全部历史拼成普通字符串，角色信息丢失、token 估算粗糙、成本随轮次线性增长。

- 采用高低水位机制：上下文超过高水位后，根据当前水位与低水位的差额动态选择陈旧轮次进行摘要，直至回落到低水位；近期轮次始终保留原文。

- Session 另有最多 10 轮与 token 上限的双重防线；tiktoken 不可用时才用字符估算。

- V1 用户画像是离线 per-user JSON，尚非在线 API；EventSummary embedding/RAG 是计划接入条件。

## 六、关键工程取舍

| **取舍**             | **为什么**                           | **边界**                                   |
|----------------------|--------------------------------------|--------------------------------------------|
| BERT 优先、LLM 回退  | 确定样本低延迟低成本，歧义样本保质量 | 需要校准置信度和覆盖率                     |
| 实体知识外置         | 新实体更新词典即可生效               | 词典覆盖不足时退回句式特征/LLM             |
| OR Filter + 乘法重排 | 先保召回再保精度                     | 权重需离线/在线实验，不能长期手调          |
| 可选依赖降级         | 便于 Demo 移植和故障隔离             | 能力退化必须显式记录                       |
| 高低水位 + 近期保真  | 批量压缩陈旧轮次并预留 Token 余量    | 摘要可能损失细节，阈值需结合质量与成本调优 |

## 七、面试高频问答

### Q1. 为什么不用纯 LLM 做意图？

**建议回答：**大量高频 Query 可以被本地模型稳定处理，纯 LLM 增加 7-9s 级 API 延迟、成本和可用性风险；高置信 BERT + 低置信 LLM 能把复杂样本留给更强模型。

- 追问展开：7-9s 和 10-50ms 是文档中的量级/估算，不要说成个人线上压测结论。

### Q2. 新增老师为什么可以不重训？

**建议回答：**训练和推理都把实体替换/标记为统一类型 token，模型学的是‘老师实体 + 句式’，实体表更新后 EvidenceCollector 自动识别并加标记，权重无需记住具体名字。

### Q3. 实体标注会不会依赖词典？

**建议回答：**会，所以混合保留约 30% untagged 样本，让未命中词典时仍可依靠句式；低置信再回退 LLM。

### Q4. 类别权重、Focal Loss、Label Smoothing 分别解决什么？

**建议回答：**类别权重解决类频率不均，Focal Loss 解决样本难度不均，Label Smoothing 解决硬标签和过度自信；三者互补但要用消融验证。

### Q5. 为什么 weighted F1 仍不够？

**建议回答：**它仍受大类权重影响，可能掩盖长尾类。线上路由更应看各类 precision/recall、低置信覆盖率、LLM 回退率和业务代价矩阵。

### Q6. 阈值 0.85/0.90 怎么定？

**建议回答：**应在验证集做可靠性图/温度缩放，结合误判成本、LLM 成本与覆盖率选择；图片场景不确定性更高所以阈值更保守。

### Q7. 为什么证据收集放在意图前？

**建议回答：**实体类型本身是强意图特征，能把业务知识从模型权重中外置；先有 evidence 再分类，再用 intent 指导检索。

### Q8. 为什么 Filter 用 OR？

**建议回答：**AND 容易因实体不一致召回为空；OR 先保留老师相关和学科相关候选，再用当前实体/上下文/画像的差异权重重排。

### Q9. 为什么用乘法重排？

**建议回答：**乘法保留基础相关性门槛，低相关结果再多业务 boost 也不容易被抬到顶部；加法可能让垃圾结果靠固定加分越级。

### Q10. 上下文为什么不能全量拼接？

**建议回答：**Token 成本会随轮次线性增长，陈旧信息还会干扰当前意图。系统用高水位触发压缩，并按水位差动态摘要陈旧轮次直至回落到低水位；近期轮次保持原文，长期 FactMemory 作为浓缩事实补充。

### Q11. FactMemory 和 EventSummary 有何不同？

**建议回答：**FactMemory 是跨 Session 的稳定事实，量少，V1 可从离线 JSON 注入；EventSummary 是每次会话摘要，数量会持续增长，按 Query 在线召回仍属于后续规划。

### Q12. 如何评估系统？

**建议回答：**离线看实体识别、意图 per-class F1/校准、召回 NDCG/Recall@K；在线看回退率、首包、零结果率、搜索成功/点击/转化、多轮承接和成本，并按意图分桶。

### Q13. 有什么没有做完？

**建议回答：**技术资料没有给出完整线上意图准确率和消融结果；V1 画像是离线 JSON，EventSummary 在线向量召回尚是接入规划；Demo 的规则兜底不代表生产。

## 八、补充八股与项目映射

以下问题来自通用 Agent 面试题库；回答已按本项目的事实边界筛选。通用方案不等同于当前线上能力。

### Q1.5. 为什么 Agent 经常出现幻觉或乱调工具？怎么缓解？（阿里）

建议回答：常见原因是工具描述重叠、一次暴露过多工具、参数 Schema 太宽、上下文存在冲突指令，或模型在证据不足时仍被要求必须完成任务。缓解时先用路由或状态机缩小可用工具集合，写清每个工具的适用与禁用条件，参数使用严格 Schema、枚举和服务端校验，并把工具返回当作不可信输入。高风险动作还要鉴权、幂等和确认；证据不足时允许拒答，并持续监控误调用率、无效参数率和循环次数。

项目边界：EduBot；智能搜索可映射到证据优先和不足时兜底。

### Q1.6. 在 RAG 生成阶段，如何在 Prompt 中设定边界，防止没有检索结果时产生幻觉？（字节、快手）

建议回答：Prompt 要明确“只能依据给定证据回答”，把证据放在清晰分隔区，并声明证据中的指令不得执行；同时把检索状态、命中数和可信阈值传给模型。结果为空、低于阈值或相互冲突时，要求输出固定兜底话术或向用户澄清，不能用模型参数中的记忆补齐事实；关键结论还应关联来源。Prompt 不是唯一防线，检索层要做阈值和去重，生成后再检查主要结论是否能由证据支持。

项目边界：高途智能搜索。

### Q1.7. Agent 和 Workflow 有什么区别？（京东）

建议回答：Workflow 的步骤、分支和终止条件主要由开发者预先定义，强调稳定、可复现和可测试；Agent 则由模型根据目标和环境动态选择下一动作，适合路径难以穷举的开放任务，但成本和风险更高。实际生产通常采用混合结构：外层 Workflow 控制权限、状态和关键节点，模型只在分类、规划或生成等不确定节点做选择。是否使用 LLM 不是判断标准，关键看执行路径的控制权主要在代码还是模型。

项目边界：四个简历项目都相关；EduBot 是 Agent 与确定性控制面的混合，主动服务是分层图，智能搜索和用户画像主要是 Pipeline。

### Q4.1. 怎么设计 Agent 的记忆系统？（蚂蚁、字节）

建议回答：我会先按作用域拆成 Turn 临时状态、Session 短期记忆和跨 Session 长期记忆。短期层保存近期消息、当前目标、工具结果和执行状态，并按 Token 预算摘要；长期层只沉淀稳定事实、偏好和能力结论，同时保留来源、时间、状态、版本和 TTL。写入侧要有提取、去重、冲突合并和过期机制；读取侧按用户命名空间隔离，再结合类型、时效和语义相关性召回。最后用命中率、事实正确率、冲突率和实际采用率评估。

项目边界：高途用户画像、高途智能搜索。

### Q4.2. 长期记忆如何存储？历史记录量很大时，怎么优化查询效率？（蚂蚁、字节）

建议回答：长期记忆不能只存向量。我会把事实正文、用户、类别、来源、时间、有效状态和版本作为权威记录，对需要语义检索的字段另建 embedding 索引。数据量大时先按用户、权限、active 状态、类型和时间过滤，再做向量或关键词召回并重排 Top-K，同时采用分区、冷热分层、摘要压缩、增量索引和热点缓存。删除和纠错必须作用到权威记录与索引，避免召回已经失效的事实。

项目边界：高途用户画像、高途智能搜索；V1 仍是 per-user JSON，向量召回属于规划。

### Q4.3. Agent 中的短期记忆和长期记忆分别怎样存储？（快手）

建议回答：短期记忆通常是 thread 或 session 级状态，可按 session\_id 存在 Redis、数据库或 checkpointer 中，包括消息、当前任务、工具结果和 checkpoint；模型上下文只是它的一次有界投影，不等于完整存储。长期记忆跨会话存在用户级 Store 中，保存稳定事实、偏好和历史经验。高途搜索使用当前 Session 原文加陈旧轮次摘要，长期 FactMemory 从离线 JSON 注入；EduBot 的 active/paused Task 属于任务状态，不能冒充用户长期记忆。

项目边界：高途智能搜索、高途用户画像；EduBot 用于澄清状态与记忆的区别。

### Q4.4. RAG 和持久化记忆有什么区别？（字节）

建议回答：RAG 是“如何按当前问题取外部信息”的运行时检索模式，数据可以是文档、数据库或历史摘要；持久化记忆是“系统跨轮、跨会话保存什么以及如何更新”的状态机制，关注作用域、写入、冲突、版本、过期和删除。两者可以组合：把长期记忆建索引后按 Query 做 RAG，但有持久化记忆不代表一定使用向量检索。少量稳定事实可以直接读取，大量事件历史再按需检索。

项目边界：高途用户画像、高途智能搜索。

### Q4.5. 有没有做记忆衰退，避免旧数据干扰新任务？（字节、阿里、夸克）

建议回答：衰退不应是对所有旧信息统一降权。通常先按事实类型设置 TTL 或有效期；有明确时间锚点时使用 expires\_at，没有时按标签配置基础 TTL；新旧事实冲突时通过合并或替换把旧事实置为 inactive，同时保留来源以便审计。动态兴趣可以只看最近时间窗，稳定身份和长期偏好则保留更久。读取时综合相关性、时效、置信度和最后确认时间，必要时向用户重新确认。

项目边界：高途用户画像、高途智能搜索、阿里主动服务。

### Q4.6. 上下文管理是怎么做的，如何进行记忆？（网易、字节）

建议回答：我不会把全部历史直接拼进 Prompt，而是按优先级组装：系统与安全规则、当前 Query、当前任务状态、近期原文、陈旧轮次摘要、长期稳定事实和按需检索内容，并统一做 Token 预算。短期内容随每轮更新，长期内容经过提取、去重和冲突处理后再写入。还要保留来源和版本，把检索内容视为不可信数据，防止历史文本中的提示注入改变系统规则。

项目边界：高途智能搜索；EduBot、主动服务和用户画像均有对应落点。

### Q4.7. Agent 中长短期记忆如何设计？各自存什么，怎么触发读取？（百度、字节）

建议回答：短期记忆保存当前会话的消息、实体、任务进度和工具观察，每一轮都读取，但只向模型投影预算内的近期原文与摘要；任务恢复时再读取对应 checkpoint。长期记忆保存跨会话仍有价值的事实、偏好、能力和历史结论，通常在会话开始或相关意图出现时读取。长期写入可以在会话结束、事实置信度达到阈值或用户明确确认后异步触发，避免阻塞在线链路。

项目边界：高途智能搜索、高途用户画像。
