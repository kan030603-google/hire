# 大模型智能体面试八股

本文以三张题图中的 45 道问题为基础，并补充近期高频技术题。每题先给可直接口述的主回答，再标明与现有项目的关系。回答项目问题时，优先采用“结论、机制、项目落点、边界”的顺序；不把通用方案说成项目已实现能力。

## 1 Agent 基础概念系列

### 1.1 一个完整的 Agent 智能体架构一般包括哪些部分？（字节）

**回答：** 我通常把 Agent 拆成七部分：输入与安全门禁、模型与指令、规划或路由、工具注册与执行、短期状态和长期记忆、运行时编排、输出与观测。模型只负责提出决策或工具意图；执行器负责参数校验、权限和真实副作用；状态库保存可恢复事实；编排器控制循环、超时和终止条件。关键边界是不能把模型自然语言直接当成系统状态，真正的状态变更应由确定性控制面提交。

**项目关联：** EduBot、主动服务。

### 1.2 ReAct 范式是什么？有什么优缺点？（阿里、腾讯、美团）

**回答：** ReAct 是 Reasoning 与 Acting 交替的范式：模型基于目标和当前观察形成下一步判断，发起工具动作，再依据工具返回继续规划，直到得到答案。优点是能先查证再回答、根据环境反馈修正计划，并留下可诊断的动作轨迹；缺点是调用轮数多、时延和成本高，早期错误可能传播，还可能循环或受工具结果中的提示注入影响。生产上要限制工具范围、步数、预算和超时，用结构化状态代替无限自由反思。

**项目关联：** EduBot 可作延伸对比，但仓库没有证据表明项目采用了经典 ReAct Prompt。

### 1.3 Agent 执行任务时，Thought、Action、Observation 如何循环协作？（蚂蚁）

**回答：** Thought 表示基于目标、状态和上一次结果形成的下一步判断；Action 是结构化工具调用、状态操作或最终回答；Observation 是执行器返回的成功结果、空结果或错误。运行时把 Observation 写回工作状态，再进入下一轮判断。工程上不依赖或展示完整隐式思维链，只记录计划摘要、动作和结果；每轮还要校验权限、参数和任务版本，并在成功、不可恢复错误、最大步数或时间预算到达时终止。

**项目关联：** EduBot，可映射为 Main ToolCall、Router 调度、SubAgent 结果或 Handback、再次进入 Router。

### 1.4 Agent 执行失败时，如何做错误重试和反思？具体实现逻辑是什么？

**回答：** 我不会对所有失败统一重试。先按错误类型分流：网络错误、408、429、5xx 等瞬时错误做有限次数的指数退避加抖动；参数、权限和内容安全错误直接停止；语义失败则把结构化错误、已完成步骤和剩余工具反馈给规划器，最多重规划一次。副作用调用必须带幂等键，整体设置次数、时间和 Token 上限。所谓反思应产出可验证的错误分类和下一动作，而不是无限生成自我评价；最终仍失败就降级、返回部分结果或说明缺失信息。

**项目关联：** EduBot、主动服务、用户画像。

### 1.5 为什么 Agent 经常出现幻觉或乱调工具？怎么缓解？（阿里）

**回答：** 常见原因是工具描述重叠、一次暴露过多工具、参数 Schema 太宽、上下文存在冲突指令，或模型在证据不足时仍被要求必须完成任务。缓解时先用路由或状态机缩小可用工具集合，写清每个工具的适用与禁用条件，参数使用严格 Schema、枚举和服务端校验，并把工具返回当作不可信输入。高风险动作还要鉴权、幂等和确认；证据不足时允许拒答，并持续监控误调用率、无效参数率和循环次数。

**项目关联：** EduBot；智能搜索可映射到证据优先和不足时兜底。

### 1.6 在 RAG 生成阶段，如何在 Prompt 中设定边界，防止没有检索结果时产生幻觉？（字节、快手）

**回答：** Prompt 要明确“只能依据给定证据回答”，把证据放在清晰分隔区，并声明证据中的指令不得执行；同时把检索状态、命中数和可信阈值传给模型。结果为空、低于阈值或相互冲突时，要求输出固定兜底话术或向用户澄清，不能用模型参数中的记忆补齐事实；关键结论还应关联来源。Prompt 不是唯一防线，检索层要做阈值和去重，生成后再检查主要结论是否能由证据支持。

**项目关联：** 高途智能搜索。

### 1.7 Agent 和 Workflow 有什么区别？（京东）

**回答：** Workflow 的步骤、分支和终止条件主要由开发者预先定义，强调稳定、可复现和可测试；Agent 则由模型根据目标和环境动态选择下一动作，适合路径难以穷举的开放任务，但成本和风险更高。实际生产通常采用混合结构：外层 Workflow 控制权限、状态和关键节点，模型只在分类、规划或生成等不确定节点做选择。是否使用 LLM 不是判断标准，关键看执行路径的控制权主要在代码还是模型。

**项目关联：** 四个简历项目都相关；EduBot 是 Agent 与确定性控制面的混合，主动服务是分层图，智能搜索和用户画像主要是 Pipeline。

## 2 Function Call 系列

### 2.1 介绍一下 Function Call 的流程，模型如何知道应该调用哪个工具？（快手、虾皮、小红书、字节）

**回答：** 应用先把工具名称、用途、参数 Schema 和约束随请求提供给模型；模型结合用户意图、系统指令和工具描述，选择直接回答或生成结构化 ToolCall。应用收到后做 Schema、权限和业务校验，真实执行工具，再用对应 call_id 把 ToolResult 传回模型；模型据此生成答案或继续调用。模型不知道函数内部实现，只根据元数据做概率选择，因此宿主还要用工具白名单、tool choice 和状态机控制实际可调用范围。

**项目关联：** EduBot 的 Main ToolCall Handoff。

### 2.2 Function Call 返回的 JSON 不标准怎么解决？（阿里）

**回答：** 优先使用原生 Function Calling、严格 JSON Schema 或 Structured Outputs，而不是让模型自由生成一段“像 JSON”的文本。服务端仍要解析并做 Schema 校验，拒绝未知字段、错误类型和非法枚举；失败时把精简的字段级错误返回模型，允许有限次数修复。语法层只能做确定性的安全归一化，涉及下单、写库等副作用时不能猜测参数；超过重试上限就受控失败，并记录原始输出、模型版本和 Schema 版本。

**项目关联：** EduBot。

### 2.3 工具调用超时或返回空值时，如何设计 Prompt 让 Agent 反馈用户？（快手）

**回答：** 工具应统一返回结构化状态，例如 success、empty、timeout、error，并附带是否可重试和哪些信息可以向用户公开；Prompt 明确禁止把失败解释成“业务数据不存在”。瞬时超时且调用幂等时可以有限重试，再尝试缓存或备用工具；真实空结果则说明当前条件下未查到，并建议用户补充范围。写操作的提交状态不确定时不能盲目重试，应先查询状态。最终只向用户说明影响和下一步，不泄露堆栈、密钥或内部服务名。

**项目关联：** EduBot；主动服务有相似的超时静默降级，但它不是 Function Call 项目证据。

### 2.4 多个工具调用链路如何调度？是否有异常 fallback 策略？（阿里、淘天）

**回答：** 先把调用关系建成依赖图：有数据依赖的步骤串行，无依赖的只读步骤可以并行；调度器再根据意图、当前状态、权限、成本和时延预算选择工具。每次调用都带 call_id、deadline、幂等键和状态，结果标准化后再进入下一步。可选工具失败时可跳过、切缓存或备用源并返回部分结果；关键工具失败则停止后续依赖。整体还要限制调用次数和循环深度，并用链路追踪区分选择错误、执行失败和降级成功。

**项目关联：** EduBot；当前项目是一轮一个 Handoff Tool，任意多工具 DAG 属于通用方案，不是一期现状。

### 2.5 大模型经常捏造工具调用参数，怎么处理？（阿里）

**回答：** 参数不能由模型单方面决定。定义工具时尽量使用严格 Schema、枚举、长度和格式限制，关闭额外字段；用户可读名称先由服务端解析成真实 ID，不允许模型编造数据库主键、路径或权限。调用前执行 Schema、业务范围、资源存在性和授权校验；缺少关键值时向用户澄清，非法值返回字段级错误，最多修复一次。高风险写操作增加预览确认和幂等键，确保重复调用不会产生重复副作用。

**项目关联：** EduBot。

## 3 MCP 与 Skill 系列

### 3.1 MCP 和 Skill 的区别是什么？（小红书、阿里、淘天）

**回答：** MCP 是宿主、客户端和外部服务之间交换能力与上下文的协议，解决工具如何发现和调用、资源如何读取以及结果怎样返回。Skill 是可复用的工作方法包，通常包含任务指令以及可选脚本、参考资料和模板，解决 Agent 面对某类任务时应该按什么流程工作。前者偏连接和运行时能力，后者偏知识与操作规范；Skill 可以调用 MCP 暴露的工具，但两者互不替代，也都不等于模型本身。

**项目关联：** 通用题；当前项目材料没有使用 MCP 或 Skill 的证据。

### 3.2 MCP 协议是干什么的？怎么理解？（美团）

**回答：** 可以把 MCP 理解为 AI 应用连接外部能力的标准接口层，类似开发工具生态中的 LSP。它采用 Host、Client、Server 架构，以 JSON-RPC 表达消息，服务端可暴露 Tools、Resources 和 Prompts，并通过能力协商声明支持范围。它标准化发现、调用、结果、进度和错误，但不规定模型如何推理或何时调用工具，也不能替代权限控制、用户授权和业务状态机。

**项目关联：** 通用题。

### 3.3 Skill、MCP 和 Rule 的区别是什么？（美团）

**回答：** 三者回答不同问题：Skill 回答“这类任务按什么方法做”，MCP 回答“外部数据和工具如何标准接入”，Rule 回答“哪些行为必须、禁止或需要审批”。Rule 不是统一的跨产品协议，不同 Agent 产品的实现可能不同。典型运行顺序是 Rule 先限制边界，Skill 组织步骤，步骤再使用本地工具或 MCP 工具。Skill 不能绕过 Rule，MCP 也只提供能力，不自动赋予调用权限。

**项目关联：** 通用题。

### 3.4 Function Calling、MCP、Tool Use 三者是什么关系？（虾皮、携程、字节）

**回答：** Tool Use 是上层概念，指模型借助外部能力完成任务；Function Calling 是模型 API 中表达工具选择和结构化参数的一种机制；MCP 是宿主与工具提供方之间进行发现、连接和调用的协议。典型链路是宿主从 MCP Server 获取工具定义，注册给模型，模型生成 Function Call，宿主校验后发起 MCP tools/call，再把结果反馈给模型。Function Calling 也可以直接调用本地函数，不必经过 MCP。

**项目关联：** EduBot 可用来解释 ToolCall，但该项目没有使用 MCP。

### 3.5 “MCP 2.0”或下一代 MCP 是什么？2026-07-28 版相比旧版升级了哪些地方？

**回答：** 先澄清版本口径：MCP 规范按日期版本化，官方名称是 `2026-07-28`；“MCP 2.0”通常是对这次大版本升级或对应 v2 SDK 的非正式称呼。相比 `2025-11-25` 及更早版本，最核心的变化是从依赖双向连接的有状态会话改成无状态请求/响应：移除 `initialize/initialized` 握手和 `Mcp-Session-Id`，每个请求都在 `_meta` 中携带协议版本、客户端身份和能力，能力发现改为可选的 `server/discover`，因此请求可以落到任意实例，更容易水平扩容。交互上用 Multi Round-Trip Requests（MRTR）的 `input_required` 和 `inputResponses` 承载确认、补参等多轮需求，不再要求服务器主动请求并长期占用双向流。工程上新增 `Mcp-Method`、`Mcp-Name` 等标准请求头，方便网关直接做路由、鉴权、限流和计量；列表结果增加 `ttlMs`、`cacheScope` 和确定性顺序，便于缓存。生态上正式建立扩展框架，Tasks 扩展支持长耗时任务的轮询与更新，通知统一到 `subscriptions/listen`；安全上增加 OAuth issuer 校验和凭证绑定，并推动 CIMD 替代 DCR。Roots、Sampling、Logging 以及旧 HTTP+SSE 进入弃用期。可以概括为：旧版优先解决“能力如何标准接入”，新版进一步解决“如何无状态扩缩容、通过网关治理、支持长任务和安全上线”。迁移时要做协议版本协商或双栈兼容，不能只升级 SDK 包名。

**项目关联：** 通用题；当前项目材料没有使用 MCP，不能把上述能力说成项目已落地。

## 4 记忆与上下文管理系列

### 4.1 怎么设计 Agent 的记忆系统？（蚂蚁、字节）

**回答：** 我会先按作用域拆成 Turn 临时状态、Session 短期记忆和跨 Session 长期记忆。短期层保存近期消息、当前目标、工具结果和执行状态，并按 Token 预算摘要；长期层只沉淀稳定事实、偏好和能力结论，同时保留来源、时间、状态、版本和 TTL。写入侧要有提取、去重、冲突合并和过期机制；读取侧按用户命名空间隔离，再结合类型、时效和语义相关性召回。最后用命中率、事实正确率、冲突率和实际采用率评估。

**项目关联：** 高途用户画像、高途智能搜索。

### 4.2 长期记忆如何存储？历史记录量很大时，怎么优化查询效率？（蚂蚁、字节）

**回答：** 长期记忆不能只存向量。我会把事实正文、用户、类别、来源、时间、有效状态和版本作为权威记录，对需要语义检索的字段另建 embedding 索引。数据量大时先按用户、权限、active 状态、类型和时间过滤，再做向量或关键词召回并重排 Top-K，同时采用分区、冷热分层、摘要压缩、增量索引和热点缓存。删除和纠错必须作用到权威记录与索引，避免召回已经失效的事实。

**项目关联：** 高途用户画像、高途智能搜索；V1 仍是 per-user JSON，向量召回属于规划。

### 4.3 Agent 中的短期记忆和长期记忆分别怎样存储？（快手）

**回答：** 短期记忆通常是 thread 或 session 级状态，可按 session_id 存在 Redis、数据库或 checkpointer 中，包括消息、当前任务、工具结果和 checkpoint；模型上下文只是它的一次有界投影，不等于完整存储。长期记忆跨会话存在用户级 Store 中，保存稳定事实、偏好和历史经验。高途搜索使用当前 Session 原文加陈旧轮次摘要，长期 FactMemory 从离线 JSON 注入；EduBot 的 active/paused Task 属于任务状态，不能冒充用户长期记忆。

**项目关联：** 高途智能搜索、高途用户画像；EduBot 用于澄清状态与记忆的区别。

### 4.4 RAG 和持久化记忆有什么区别？（字节）

**回答：** RAG 是“如何按当前问题取外部信息”的运行时检索模式，数据可以是文档、数据库或历史摘要；持久化记忆是“系统跨轮、跨会话保存什么以及如何更新”的状态机制，关注作用域、写入、冲突、版本、过期和删除。两者可以组合：把长期记忆建索引后按 Query 做 RAG，但有持久化记忆不代表一定使用向量检索。少量稳定事实可以直接读取，大量事件历史再按需检索。

**项目关联：** 高途用户画像、高途智能搜索。

### 4.5 有没有做记忆衰退，避免旧数据干扰新任务？（字节、阿里、夸克）

**回答：** 衰退不应是对所有旧信息统一降权。通常先按事实类型设置 TTL 或有效期；有明确时间锚点时使用 expires_at，没有时按标签配置基础 TTL；新旧事实冲突时通过合并或替换把旧事实置为 inactive，同时保留来源以便审计。动态兴趣可以只看最近时间窗，稳定身份和长期偏好则保留更久。读取时综合相关性、时效、置信度和最后确认时间，必要时向用户重新确认。

**项目关联：** 高途用户画像、高途智能搜索、阿里主动服务。

### 4.6 上下文管理是怎么做的，如何进行记忆？（网易、字节）

**回答：** 我不会把全部历史直接拼进 Prompt，而是按优先级组装：系统与安全规则、当前 Query、当前任务状态、近期原文、陈旧轮次摘要、长期稳定事实和按需检索内容，并统一做 Token 预算。短期内容随每轮更新，长期内容经过提取、去重和冲突处理后再写入。还要保留来源和版本，把检索内容视为不可信数据，防止历史文本中的提示注入改变系统规则。

**项目关联：** 高途智能搜索；EduBot、主动服务和用户画像均有对应落点。

### 4.7 Agent 中长短期记忆如何设计？各自存什么，怎么触发读取？（百度、字节）

**回答：** 短期记忆保存当前会话的消息、实体、任务进度和工具观察，每一轮都读取，但只向模型投影预算内的近期原文与摘要；任务恢复时再读取对应 checkpoint。长期记忆保存跨会话仍有价值的事实、偏好、能力和历史结论，通常在会话开始或相关意图出现时读取。长期写入可以在会话结束、事实置信度达到阈值或用户明确确认后异步触发，避免阻塞在线链路。

**项目关联：** 高途智能搜索、高途用户画像。

### 4.8 不同 Agent 之间的记忆如何共享？（百度）

**回答：** 我会采用“权威存储加受控投影”，不让 Agent 直接共享全部 Prompt 或私有运行时。用户级稳定事实可以共享；Topic 摘要按话题读取；Task 的目标、进度、工具状态和 checkpoint 必须按 task_id 隔离。Router 根据接收方权限只投影必要字段，交接时传递结构化摘要、来源、时间和版本，并用 ToolCall/ToolResult 闭合协议。共享状态还要有单一写入权、版本校验和审计日志。

**项目关联：** EduBot。

## 5 多智能体协作系列

### 5.1 如何让多个 Agent 协同工作？举一个具体的协同机制例子。（字节）

**回答：** 核心是统一控制面，不让多个 Agent 随意互调。以 EduBot 为例，Main 通过 ToolCall 表达移交意图，Router 创建带 task_id、topic、goal 和 owner 的任务，再调度专业 Agent；专业 Agent 完成后通过 Handback 返回，Router 补齐 ToolResult 并切回 Main。用户中途换题时，Gate 只给出 PREEMPT 建议，Router 将旧任务暂停；用户返回后再恢复原任务和进度。状态变更用 revision 和 CAS 防止旧请求覆盖新状态。

**项目关联：** EduBot。

### 5.2 多 Agent 协作常见模式有哪些？（阿里）

**回答：** 常见模式包括：Supervisor 把子 Agent 当工具统一调度；Handoff 在不同 Agent 间转移对话控制权；Router 按领域分流并可并行汇总；固定 Pipeline 按预定义步骤串联；共享黑板让多个角色围绕同一状态协作；以及辩论、评审或投票模式。选择依据是是否需要直接与用户连续对话、任务能否并行、上下文是否要隔离，以及控制权是否必须集中。EduBot 属于 Router 与 Handoff 的组合。

**项目关联：** EduBot。

### 5.3 如何保证多智能体协同的效果？（小红书）

**回答：** 不能只看接口是否成功，我会从合同、不变量和评测三层保证。合同层统一输入输出、任务身份、ToolCall 配对和失败语义；状态层保证单一 owner、版本校验、幂等、超时与迟到结果隔离；评测层同时检查路由准确性、任务迁移、最终 responder、时延和业务结果。EduBot 对 163 个多轮 Session、902 个请求做过全链路对账，技术终态基本正常，但语义抽样仍发现恢复判定和 LGI 单调性问题，说明链路成功率不能代替任务级验收。

**项目关联：** EduBot。

### 5.4 什么情况下选择单 Agent，什么情况下选择多 Agent？（快手）

**回答：** 如果任务边界单一、工具数量少、上下文可以共享，而且同一套权限和评价标准即可覆盖，我优先选择单 Agent，因为链路更短、成本和故障面更小。只有当领域知识和工具明显异构、需要不同权限或长期任务状态、需要并行处理，或者单模型因工具过多而路由不稳时，才引入多 Agent。增加 Agent 数量本身不是收益，必须用任务成功率、成本、时延和可维护性证明拆分有效。

**项目关联：** EduBot、主动服务。

### 5.5 项目中子 Agent 之间的上下文怎么传递？（阿里）

**回答：** 不应复制整段会话，而应传递最小任务包：目标、约束、当前 Query、task_id、topic、版本、必要的稳定事实、已有产物引用和期望输出 Schema。工具中间过程和未完成计划按 Task 隔离，交接方返回结果、证据、不确定性和剩余事项。EduBot 当前由 Router 投影 task_goal、previous_user、progress_summary、LGI 等有界状态；完整 task-scoped context、checkpoint_ref 和多 paused Registry 仍是目标设计。

**项目关联：** EduBot。

### 5.6 Agent 之间如何实现相互调用？（美团）

**回答：** 常见做法是把子 Agent 封装成带结构化 Schema 的工具，或者通过 Handoff 协议转移控制权。无论哪种，都应携带 task_id、call_id、deadline、幂等键和明确返回协议，避免递归调用与重复副作用。EduBot 中 Main 发出 ToolCall，由 Router 准备任务后调用 SubAgent；SubAgent 用 Handback 返回，Router 补 ToolResult 闭环。当前没有开放任意 SubAgent 直接调用另一个 SubAgent，能力切换必须回到 Router。

**项目关联：** EduBot。

### 5.7 多 Agent 协作如何做上下文管理和共享？（小红书）

**回答：** 可以把上下文分成 Session、Topic、Task 和 Turn 四层。Session 放身份、稳定偏好与公共策略；Topic 保存话题摘要和相关事实；Task 保存该次执行的目标、进度、工具状态与 checkpoint；Turn 只放本轮 Query、路由建议和流式中间状态。Main 默认读取当前 Topic 和受控的 Session 信息，SubAgent 默认只读自己的 Task，需要跨层信息时由控制面显式投影，并通过权限、版本和来源信息防止串扰。

**项目关联：** EduBot。

## 6 任务规划与分解系列

### 6.1 项目里的 Modular Agent 如何实现多步规划？（阿里、淘天）

**回答：** 通用实现可以拆成 Planner、Executor 和 State。Planner 输出结构化步骤，每步包含目标、依赖、输入、负责模块、工具和完成条件；系统先校验依赖、权限、最大步数和是否成环，再调度已经就绪的步骤。Executor 返回 Observation，状态层记录产物与错误，必要时只从失败点重规划，并在关键节点保存 checkpoint。计划应是可执行、可验证的数据结构，而不是一段无法约束的自然语言。

**项目关联：** EduBot 和主动服务仅作边界对比；两者都不是通用动态 Planner。

### 6.2 主 Agent 规划任务时，怎么保证拆解步骤合理？用了哪种 Prompt 策略？（阿里）

**回答：** 我会让模型按固定 Schema 输出 step_id、目标、依赖、所需工具、预期产物和终止条件；Prompt 中提供总目标、已知事实、约束、可用工具、禁止操作、最大步骤数和少量正确示例。生成后仍由程序校验依赖闭环、参数类型、权限和预算；执行中根据 Observation 局部重规划，而不是一次计划到底。项目中如果模型只负责路由或分类，就应明确它不是通用任务分解器。

**项目关联：** EduBot，用于说明 Main 只表达 Handoff 意图，Router 才是状态权威。

### 6.3 Agent 如何结合工具、知识和规划自主运行？

**回答：** 可以把它理解为 Goal、Plan、Act、Observe、Update 的闭环。知识通过 RAG 或结构化记忆按需进入当前状态；工具以明确 Schema、权限和超时暴露；Planner 根据目标、约束和已有 Observation 选择下一步；执行结果写回状态，满足完成条件则结束，否则修正计划或降级。生产环境还要限制最大轮数、危险工具审批、幂等和可追踪性，保证“自主”仍处在可控边界内。

**项目关联：** EduBot。

### 6.4 Modular Agent 中的多步规划如何落地？（快手）

**回答：** 我会把 Plan 持久化为可执行 DAG：节点记录依赖、状态、输入输出引用、重试策略和验收条件；Scheduler 按拓扑关系执行就绪节点，无依赖任务可以并行。每步结束把结构化结果写入 State，失败时根据错误类别重试、换工具或触发 Replan；长任务在安全点保存 checkpoint，恢复时从最后成功节点继续。还要限制重规划次数，避免模型反复改计划却没有进展。

**项目关联：** 通用设计；EduBot 和主动服务只能作为“状态机或固定图”对比。

## 7 Agent 框架与开发系列

### 7.1 LangChain 和 LangGraph 分别提供什么功能？区别在哪？（字节）

**回答：** 按当前官方定位，LangChain 是较高层的 Agent 框架，提供模型、消息、工具、Agent 循环、中间件和集成，适合快速搭建常见 Agent；LangGraph 是较低层的有状态编排运行时，用 State、Node 和 Edge 表达分支与循环，重点提供持久化、耐久执行、流式、人机协同和故障恢复。两者不是互斥关系：LangChain 的 Agent 可以运行在 LangGraph 上；简单场景从 LangChain 开始，需要精细状态机和长任务控制时再使用 LangGraph。

**项目关联：** 通用题；仓库没有使用这两个框架的证据。

### 7.2 LangGraph 相比 LangChain 有什么优势？状态快照如何实现？向量记忆库如何更新用户画像？（快手）

**回答：** LangGraph 的优势是对状态、分支、循环、暂停恢复和副作用顺序有更细控制。接入 checkpointer 后，它会在执行步骤边界按 thread_id 保存 checkpoint；StateSnapshot 包含当前 values、下一节点、配置、写入元数据和待执行任务，因此可以查询历史、从指定检查点重放或失败恢复。跨线程长期记忆使用独立 Store。画像更新仍应经过提取、Schema 校验、去重、冲突合并和版本控制，向量索引只是检索视图，不能替代权威事实库。

**项目关联：** 高途用户画像只用于对比；该项目未使用 LangGraph，V1 也没有已上线的向量记忆库。

### 7.3 Dify 和 Coze 有什么区别？

**回答：** 两者都是可视化 AI 应用平台，但选择维度不同。Dify 提供开源与自托管方案，覆盖 Agent、Workflow 或 Chatflow、知识库、模型和工具插件、API 与运行日志，适合重视数据控制、二次开发和服务集成的团队。Coze 更强调低代码智能体搭建、模板与插件生态、工作流以及面向不同入口的快速发布。实际选型应比较部署和数据治理要求、模型接入、权限、可观测性、扩展方式和运维成本，不应只比较画布体验。

**项目关联：** 通用题。

## 8 Coding Agent 系列

### 8.1 工程级 Code Agent 在处理项目上下文和生成代码时，会遇到哪些核心挑战？（蚂蚁）

**回答：** 工程级 Code Agent 的难点不在代码补全，而在闭环：要在有限上下文中定位正确文件、依赖、约定和 Git 状态；把模糊需求拆成跨文件小步并控制影响面；安全处理终端与网络权限、超时和提示注入；再用编译、静态检查、单元、集成和回归测试验证。还要保留用户未提交的改动，支持隔离、审计和回滚。因此适合采用“检索、计划、修改、验证”的循环，并设置沙箱和人工合并门禁。

**项目关联：** 通用题。

### 8.2 Claude Code 的记忆架构是什么？上下文真的等于记忆吗？（字节）

**回答：** 按官方文档，Claude Code 的新会话从新的上下文窗口开始；跨会话知识主要来自人工维护的 CLAUDE.md 和按仓库保存的 auto memory。上下文不等于记忆：上下文是本次推理可见的消息、文件、工具结果和已经召回的记忆；记忆是磁盘上的持久信息，只有加载后才会影响当前推理。上下文可能被压缩，记忆也可能过期或冲突，所以持久指令应简洁、分范围、可审计，并避免把能从代码推导的信息重复写入。

**项目关联：** 通用题。

### 8.3 AI Coding 和 AI Agent 如何一起使用，即如何用 AI Coding 开发一个 AI Agent？（字节）

**回答：** 我把 AI Coding 当作开发外环，把 AI Agent 当作产品运行内环。先定义任务、状态、工具 Schema、权限和指标，再让 Code Agent 阅读仓库，生成 Agent loop、工具适配器、Mock、测试和回放脚本，并依据执行轨迹定位问题；产品 Agent 则按“状态、决策、工具、观察、更新”运行。工程上还要补齐校验、幂等、超时重试、降级、最小权限和追踪。生成代码必须审查 Diff、运行测试并经过沙箱验证，不能让 Coding Agent 替代架构判断和生产审批。

**项目关联：** 通用题；仓库没有“实习中使用 AI Coding 开发上述项目”的证据。

### 8.4 平时用过哪些 Code Agent？有什么优缺点？（腾讯）

**回答：** 这道题必须按真实使用经历回答。当前可以确认使用过 Codex：它适合仓库级检索、跨文件修改、运行命令、检查 Diff 和测试；优势是能把分析、修改和验证连成一条工作流，缺点是长任务成本较高，选错上下文会放大后续偏差，仍需要人工 Review。只有确实使用过 Claude Code、Cursor 或其他产品后，才能补充其体验，不能把阅读资料说成实战。

**项目关联：** 通用题，回答前需本人确认实际使用经历。

## 9 Agent 训练系列

### 9.1 如何从线上真实对话构造 Expert Agent 的 SFT 训练数据？（字节）

**回答：** 我不会把线上日志直接喂给模型。先按任务、难度、轮数和成败分层采样，完成授权、PII 脱敏以及越权和注入清理；再还原系统约束、用户请求、可见状态、工具调用、工具结果和最终回答，不伪造隐藏思维链。用业务结果、可执行验证器和专家复核定义 Expert：成功轨迹用于 SFT，失败轨迹由专家修正，原失败答案可用于偏好学习。随后做 Schema 校验、去重、类别均衡，并按用户、任务和时间切分以防数据泄漏。

**项目关联：** 通用题；高途项目是 BERT 分类监督训练，不是 Expert Agent 的 LLM SFT。

### 9.2 DPO 相比 SFT 有哪些优势？Agent 任务上提升明显吗？偏好对怎么构造，自动还是人工？（蚂蚁）

**回答：** SFT 学习“应该生成什么”，适合冷启动指令、工具格式和基本能力；DPO 使用同一输入下的 chosen 与 rejected 学习相对偏好，不需要单独训练奖励模型或进行 PPO 式在线采样，通常更简单稳定，但不能替代 SFT。Agent 上是否明显提升取决于偏好质量，长轨迹仍有信用分配难题。偏好对适合人机结合：同一状态采样多条轨迹，用测试、执行器和规则自动评估成功、Schema、成本和时延，再由专家复核安全与模糊价值。

**项目关联：** 通用题。

### 9.3 对比 SFT、DPO、PPO、GRPO、RAG，说明为何选择强化学习优化 Agent，并给出评估维度、场景与依据。（淘天）

**回答：** 选型要看目标、数据、交互、算力、稳定性和知识时效。SFT 学专家示范，稳定且适合冷启动；DPO 离线学习偏好，简单但不主动探索；PPO 通过 rollout、奖励和 critic 优化长程回报，探索能力强但训练昂贵且容易受奖励漏洞影响；GRPO 用同题多输出的组内相对优势，省去独立 critic，适合有可验证奖励的任务；RAG 不更新权重，适合补充私有或快速变化的知识，但不直接教决策策略。通常先做 RAG 和 SFT，再做 DPO；只有环境可执行、轨迹奖励可靠且预算充足时才考虑 GRPO 或 PPO。

**项目关联：** 通用题。主动服务目前只有反馈与学习闭环设想，不能声称已经使用强化学习。

## 项目表达边界

- EduBot 可以讲 ToolCall、Router、Task、Handoff、Handback、CAS、异常降级和全链路审计；经典 ReAct、通用动态 Planner、完整 Task Registry、checkpoint、outbox 和任意 SubAgent 互调不能说成当前线上能力。
- 主动服务可以讲 L0-L4 分层图、异步 prepare 和下一轮 confirm、Redis、TTL、超时静默降级及反馈闭环缺口；不能说已经使用 LangGraph 或完成强化学习闭环。
- 智能搜索可以讲证据约束、BERT 与 LLM 分层意图、检索和生成路由、Token 高低水位压缩及 FactMemory 注入；完整线上指标和 EventSummary 在线向量召回仍缺证据。
- 用户画像可以讲 HistoryEvent、EventSummary、FactMemory、三层画像、TTL、冲突合并和离线 V1；不能说在线服务、Kafka、向量记忆库或 RAG 已经上线。
